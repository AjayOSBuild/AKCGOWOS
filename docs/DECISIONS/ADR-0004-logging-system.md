# ADR 0004: Unified Logging System

## Status
Accepted

## Context
Effective debugging, security auditing, and automated QEMU testing require a robust logging architecture. Logs generated by the kernel, the bootloader, core services, and the compatibility runtimes must be collected, stored, and rotated without consuming excessive disk space or blocking system execution.

## Decision

We will implement a dual-layer logging architecture: a lightweight kernel ring buffer and a centralized, structured user-space Logging Service.

### 1. Kernel & Boot Logging (Ring 0)
*   **Mechanism:** Standard Linux `printk` and the kernel ring buffer (`dmesg`).
*   **Serial Output:** During development and QEMU testing, kernel logs will be duplicated to the primary serial port (`ttyS0`) to allow the host system to capture boot diagnostics and kernel panics even if the OS filesystem fails to mount.
*   **Crash Logging:** Kernel panics will trigger a `kexec` or standard crash dump routine to save the trace to a persistent `/var/log/crash/` partition on the next successful boot.

### 2. User-Space Logging Service (Ring 3)
*   **Mechanism:** A dedicated `Logging Service` (accessible via D-Bus and standard UNIX sockets).
*   **Format:** System services will submit structured logs (JSON) containing severity, timestamp, component ID, and the message payload. 
*   **Storage:** Logs will be stored in `/var/log/os/`. To balance performance and recoverability, the current active log will be held in a memory-mapped file and synced to disk asynchronously.
*   **Rotation:** The Logging Service will automatically compress and rotate logs daily or when they exceed 50MB, preserving a maximum of 14 days of history to prevent disk exhaustion.

### 3. Application Sandbox Logs
*   **Windows/Android Compatibility:** Output from Windows (`.exe`) and Android (`.apk`) applications will be isolated. The compatibility layers will pipe application `stdout`/`stderr` into application-specific log files within their respective sandboxes (`~/.local/share/compat/logs/`), rather than flooding the primary system log.

## Consequences
*   **Positive:** Structured JSON logs enable easy parsing by automated QEMU test scripts to verify service states. Serial port duplication guarantees we capture fatal boot errors.
*   **Negative:** Enforcing structured logging requires writing custom logging macros/wrappers for all C++ core services rather than relying on standard `printf`.
